# Flash-Next option 20 live benchmark at 131,072 context - 2026-11-02

The running option 20 instance was benchmarked without restarting it: 131,072 served context, 1,024-token prefill chunks, `--verify-rows auto`, 10 GiB planner cap, DFlash2 draft attached. Seventeen timed rows covered prompt sizes from 24 to 65,451 tokens and five output styles (structured list, arithmetic, code with low reasoning, free prose, medium reasoning).

DFlash2 drafting is confirmed active on every measured request. Structured output drafts at 7.4 to 7.9 emitted tokens per decode cycle with 99 to 100 percent acceptance; reasoning-on agent-style output drafts at 2.4 tokens per cycle with 72.3 percent acceptance. Long-context prefill on this 131,072-token instance is about 10 percent slower than the same 1,024-chunk profile measured at 32,761 context on 2026-11-01, while decode speed is unchanged.

Against the 2026-11-01 1,024-chunk baseline measured at 32,761 context (`qwen38-option20-scratch-20261101.md`), the 4,019-token profile moved from 186.20 to 180.66 tok/s prefill (-3.0%), 21.59 to 22.25 s TTFT (+3.1%), and 12.38 to 11.95 tok/s decode (-3.5%). The 28,589-token profile moved from 179.65 to 161.02 tok/s prefill (-10.4%), 159.17 to 177.55 s TTFT (+11.5%), and 11.69 to 11.85 tok/s decode (+1.4%). The gap appears only in long prefill; short and medium prompts are within trial noise. The 1,024-token chunk default was selected at 32,761 served context, so a chunk re-sweep at 131,072 context is the obvious follow-up before treating 177 s TTFT at 28.6k as fixed.

Prefix reuse works as expected on this instance: repeating one 435-token prompt reused 416 cached tokens and cut TTFT from 5.20 s to 1.46 s.

## Draft acceptance by workload

Same engine, same build, same draft, requests of different output styles, 128 to 256 output tokens.

| Workload | Prompt tok | Out tok | Decode tok/s | Cycles | Tok/cycle | Drafted/accepted | Acceptance |
|---|---:|---:|---:|---:|---:|---|---:|

| Python function with docstring and doctests, reasoning low | 60 | 256 | 8.89 | 65 | 3.94 | 218/191 | 87.6% |
| Short explanatory paragraph, reasoning none | 27 | 101 | 6.07 | 47 | 2.15 | 86/53 | 61.6% |
| Three-paragraph explanation plus risk list, reasoning medium | 31 | 256 | 6.33 | 107 | 2.39 | 206/149 | 72.3% |

Reasoning-on output is the shape of traffic an agent session actually produces, and it drafts at 2.4 emitted tokens per cycle and decodes at 6.3 tok/s. That explains the 6.5 tok/s lifetime decode average in `/status`: it is workload-mixed, not a decode regression. Clean structured decode on the same instance measured 11.7 to 12.2 tok/s.

Over the seven-row long-context window the engine recorded 122,791 prefill tokens, 716 decode tokens, 162 decode batches, 614 drafted tokens and 551 accepted tokens (89.7 percent). Across the engine lifetime at snapshot time the draft context had materialized 833,344 rows and avoided 729,056 rows, and every decode batch recorded was width b1 (37,564 b1, zero b2, b3 and b4), so speculation gains come from accepted tokens per cycle rather than from wider verify batches.

## Single lane and short requests

Three concurrent 19-token requests with 24-token budgets returned in 2.02 s, 3.97 s and 5.96 s measured from submission; total wall was 5.96 s against 11.95 s of summed walls, so requests were serialized. Native `queue_to_start_ms` stayed 0.1 to 0.2 ms and native TTFT stayed about 1.5 s for all three, so the waiting happened in front-end scheduling, not in the engine queue.

Short requests pay a fixed floor: prompts of 19 to 27 tokens measured 1.45 to 1.89 s TTFT, which is why their apparent prefill rate reads only 14 to 20 tok/s. Cold 435-token prefill measured 83.6 tok/s while 939 tokens measured 134.6 to 154.3, so roughly 1.5 s of per-request setup is amortized as prompts grow.

## Memory and reliability

Metal allocated ranged from 6.92 to 7.93 GiB during the runs and peak allocated stayed 8.149 GiB. Pressure was warning and thermal was fair throughout. `vm.swapusage` reported 704.38 MiB used both before and after the first run, unchanged. No capacity failure, no Metal failure, no failed or cancelled request was recorded. The engine build ID, instance id, pid and restart count (zero, per the server log) did not change during measurement.

## Methodology and contention caveat

This machine's own agent session issues requests to the same single-lane engine, and those requests are 75,000 to 86,000 tokens with reasoning on. Two earlier runs were discarded for that reason: one aborted mid-way when a foreign request entered during the 28,672-token trial, and another timed out waiting for the engine to become idle.

Every row reported above was accepted only when all four conditions held: the engine was idle with nothing queued at trial start (measured idle wait 0.0 s), request `queue_to_start_ms` was under 100 ms (observed 0.1 to 3.5 ms), no active request with an output budget of 1,024 tokens or more was seen while the trial ran (`/status` polled every four seconds), and exactly one request completed in the trial window.

## Not measured

- Draft on versus off. `serve-native` has no draft-disabling flag; the draft comes from the install record, so a matched A/B needs a restart from a draft-free record. A second instance is not viable on this 16 GiB machine while option 20 holds about 8 GiB.
- `--verify-rows all` versus `auto` at 131,072 context, which also needs a restart.
- Anything above 65,451 prompt tokens; the 131,072-token limit was not filled.
- Sustained multi-client concurrency beyond the three-request lane probe.
