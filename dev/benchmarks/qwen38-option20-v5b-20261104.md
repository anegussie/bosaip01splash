# Option 20 V5b: closing the browser opened the second lane, and the child answered in 13 s instead of 180 s

Measured 2026-11-04 on the MacBook Air (M5, 10 cores, 16 GB unified memory), model
`ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-GGUF:IQ3_XXS` with the DFlash2 draft, served on port 1235 as
`qwen3.8-flash-next-iq3-xxs-splash`.

This row changed nothing about the server. It is the same process V5c ran (`pid 42709`, `131072`
context, a 9G cap, a 16 GiB cache quota, `--max-active-requests 2`, `SPLASH_FLASH_NEXT_SECOND_LANE_BELOW_GATE=1`),
and the only change is what else the Mac was running: Chrome with its helpers (1.42 GiB) and LM Studio
(0.39 GiB) were quit. Rows come from `build/validation/option20-v5b-20261104/run_v5b.py`, the V5
harness copied forward. Condensed data: `dev/benchmarks/qwen38-option20-v5b-20261104.json`.

## The host budget flipped, and so did the governor

| While the engine idled | V5c, browser open | V5b, browser closed |
|---|---|---|
| `host_spare_bytes` | 1.75-1.92 GiB | 3.13-3.35 GiB |
| `host_headroom_bytes` | 0.00-0.26 GiB | 1.13-1.28 GiB |
| `growth_allowed` | false | **true** |
| swap in use | 2,043 MiB | 524 MiB |
| `denied_reservations` | 1,876 | 2,727 (80 new across the whole run) |

`growth_allowed` had been false in every configuration measured on this Mac - 11G, 10G, 9G - and here it
was true with nothing touched but the app list. `memory_pressure` still reads `warning`, which is the
steady state of this machine with a 9 GiB engine resident, so the governor's own headroom margin, not
its pressure reading, is what gates a held request.

## The child started while the parent was still prefilling

Server log, one clean probe:

```
10:10:24 Started · input 28,589 · cached 0 · effort none · thinking off
10:10:36 Started · input 20 · cached 0 · effort none · thinking off
10:10:36 Memory: growth available; resource wait cleared
10:10:38 Done · input 20 · cached 0 · output 3 · prefill 20/1.52s · PP 13.1 tok/s
           · decode 2/0.48s · TTFT 12.6s · TPS 4.1 tok/s · request=56
           · frontend_queue=0.000s · native_queue=9.199s · native_wall=11.161s
10:13:35 Done · input 28,589 · cached 0 · output 114 · prefill 28,589/181.97s
           · PP 157.1 tok/s · decode 113/9.55s · TPS 11.8 tok/s · request=55 · 7.5 tok/cycle
```

The child was admitted ten seconds into its parent's 182-second prefill and finished thirteen seconds
after it was submitted. The parent was untouched by sharing the machine: 157.1 tok/s of prefill and
11.8 tok/s of decode, inside the range the uncontended 9G and 10G runs produced.

| Child queue time in the parent-child probe | |
|---|---|
| V4 (11G, 2 lanes) | 186,500 ms |
| V5 (10G, 2 lanes) | 180,264 ms |
| V5c (9G, 2 lanes) | 165,268 ms |
| V5b (9G, 2 lanes, browser closed) | **11,050 ms** |

`max_concurrent_prefilling` reached 2, which had never been seen, and the scheduler recorded its first
width-two decode batches since the engine started: `decode_batches_by_width` b1 12,987, **b2 21**, b3 0,
b4 0. `lane-probe` - three small requests submitted together - came back with `overlap_ratio` 1.079 in
the first run and 1.16 in the clean rerun, meaning total wall time (6.11 s) was *below* the sum of the
individual walls (7.09 s). In V4, V5 and V5c that ratio was 0.996-0.997, which is serialization.

## What concurrency costs: half the drive each

The row that got contaminated is the most useful one here. `decode-512` ran with a foreign request
sharing the lane (`foreign_active_samples: 6`), and its decode collapsed:

| Row | TTFT | prefill | decode | MB per decode token |
|---|---|---|---|---|
| decode-512, two requests in flight | 5,358 ms | 81.2 tok/s | **5.17 tok/s** | 611.9 MB |
| 28k-cold, clean | 189,059 ms | 151.2 tok/s | 11.55 tok/s | - |
| 28k-hit, clean | 1,177 ms | cache hit | 11.43 tok/s | 527.6 MB |

Two requests decoding together each moved at about half the single-request rate. That is what a drive
supplying 5-6 GB/s does when two lanes each demand 450-620 MB per emitted token: the bandwidth is split
rather than added. Concurrency on this Mac therefore buys queue latency - which is the whole point of a
second lane, and the reason subagent children stalled before - and not aggregate throughput.

## The margin is thin, and this session eats it

`growth_allowed` is not a stable property of this machine. After the probe, with this agent session's own
request in flight (`Started · input 108,858 · cached 108,160`), the same server read:

```
limit 9.00 GiB · charged 8.30 · cap headroom 0.70 · host spare 2.85
host headroom 0.85 GiB · growth_allowed False · denied_reservations 3,778
```

One 108,858-token conversation costs about 1.4 GiB of KV on this model (13.24 KiB per token), which is
enough to push host headroom from 1.2 GiB back under the 1 GiB margin. Two facts follow. First, at the 9G
cap the lane is available on a 16 GB Mac only while the host keeps roughly 3.15 GiB spare, which means a
browser-class app has to stay closed. Second, at the 10G default cap the plan charges about 0.6 GiB more
(resident KV 196,601 tokens against 114,681), so the same free-memory trick has to clear more: with
Chrome and LM Studio gone, host spare lands near 4.0 GiB and headroom near 1.9 GiB, which should hold
even with a long conversation resident - that configuration has not been measured yet, and it is the next
row.

## Recommendation this changes

`--max-active-requests 2` at 131,072 context on 16 GB is no longer structurally impossible, as V5c
concluded. It is conditional on host memory the launcher cannot see: the engine needs its 1 GiB of host
headroom, and on a 16 GB Mac that has to be made by not running the browser. The default should stay 1 -
the launcher cannot know which apps are open, and a second lane halves per-request decode speed when two
requests genuinely overlap. The gate override is now a supported configuration with measured numbers
behind it rather than a diagnostic, and the honest summary for delegation throughput on this machine is:
close the browser, or move to 24 GB.
