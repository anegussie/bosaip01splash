# Option 20 V3: a 4 GiB expert floor, an 11 GiB cap, and a 16 GiB SSD quota

Measured on 2026-11-03 on the MacBook Air (M5, 10 cores, 16 GB unified memory), engine build
`src-6a06f0d6`, model `ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-GGUF:IQ3_XXS` with the DFlash2 draft,
served on port 1235 as `qwen3.8-flash-next-iq3-xxs-splash`.

```sh
SPLASH_FLASH_NEXT_MAX_MEMORY=11G SPLASH_FLASH_NEXT_EXPERT_MEMORY=4G \
SPLASH_FLASH_NEXT_MAX_CACHE_DISK=16G bash /Users/mymac/startllamacpp.sh --direct 20
```

Engine argv tail: `131072 11811160064 17179869184 --persistent-cache on --cache-dir
~/Library/Caches/Splash/flash-next-option20-iq3-xxs --prefill-chunk-tokens 1024 --state-format bf16
--resource-wait-timeout 60 --ple-memory 67108864 --expert-memory 4294967296`.

Rows come from `build/validation/option20-v1-20261103/run_v3.py` against the live server, cold rows
with a fresh `cache_salt`, the repeat row holding V3's own salt fixed, 10 s cooldowns, bounded
count-to-30 and ORCHID probes. All four rows report `clean: true` and `foreign_active_samples: 0`.
Condensed row data: `dev/benchmarks/qwen38-option20-v3-20261103.json`.

## Speed did not move

| Row | V1 (10G cap, auto, 8G disk) | V2 (11G cap, 2G floor, 8G disk) | V3 (11G cap, 4G floor, 16G disk) |
|---|---|---|---|
| decode-512 TTFT | 5,338 ms | 5,288 ms | 5,448 ms |
| decode-512 decode | 12.23 tok/s | 11.86 tok/s | 11.69 tok/s |
| 28,589 tok cold TTFT | 181,320 ms | 184,130 ms | 189,767 ms |
| 28,589 tok cold prefill | 157.7 tok/s | 155.3 tok/s | 150.7 tok/s |
| 28,589 tok repeat TTFT | 1,204 ms | 1,163 ms | 1,178 ms |
| 65,451 tok cold TTFT | 445,737 ms | not run | 436,382 ms |
| 65,451 tok cold prefill | 146.7 tok/s | not run | 150.0 tok/s |
| expert reads per emitted token | 452 MB | 506 MB | 510-546 MB |

Decode stayed at 11.5-11.7 tok/s, prefill at 150-151 tok/s, and speculation held at 7.39-7.53 tokens
per cycle with 0.94-1.00 draft acceptance. Each decode cycle therefore streams about 3.8-4.0 GB
(7.4 tokens x 520 MB) at 1.5-1.6 cycles per second, which is the 6 GB/s the drive measured supplying.
Nothing in this row set moved the machine off that ceiling.

The streamed bytes did change, and not in the machine's favour. V1 read 452 MB of experts per emitted
token at 12.23 tok/s, 5.53 GB/s of drive traffic; V3 read 510-546 MB per token at 11.5-11.7 tok/s,
6.06 GB/s. The drive supplied 10% more and the model produced 5% fewer tokens per second. The store
was the same 512 slots in both runs, so the extra bytes are streaming overhead, not new residency,
and the only counters that could pay for it (`shrinks`, `regrows`, `hit_rate`) never moved from 0,
0 and 0.00.

## The expert store is not the flag's to give

The startup log said it before any request ran:

```
Routed experts stream from their files: 512 slots for 24576 experts (2%) in 1262 MiB, a store of
1992 MiB in 1 chunks, all that the floors, its own among them, leave it beside the KV kept resident;
it gives none back, its floor, the 4096 MiB --expert-memory sets (1992 MiB in whole slots and chunks),
being all of it.
```

`/status` matched at both ends of the run: `cap_bytes` = `floor_bytes` = 2,089,468,688, 512 of 24,576
slots, `chunks 1`, `cap_chunks 1`, `shrinks 0`, `regrows 0`, 29-42 resident, `hit_rate` 0.00. Same
store as the 2 GiB floor of V2 and the same store as `auto` at a 10 GiB cap. The requested number is
a floor that the plan rounds **down** to the whole slots and chunks the memory plan leaves it, so a
larger request cannot enlarge it.

The other startup line names who takes the rest:

```
Long requests keep their KV on the SSD cache: 262144 tokens of context (bound: model; window 262144,
resident 262137, spilled 262144, disk 262144); a request whose KV fits 2993 MiB stays in memory;
hot block cache 390 MiB (floor 390 MiB); SSD room for active KV 16.0 GiB.
```

`resident 262137` tokens is the resident KV allowance, sized against the model's 262,144-token
window rather than the 131,072 tokens this profile serves. `planSpill()` in
`runtime/engine/MemoryPlan.cpp:115-172` binary-searches the longest context whose spill floors fit
what the other floors leave, and on this Mac the whole window fits, so the floors keep 262,137 tokens
of INT8 KV (3.47 GiB of capacity, `memory_plan.budget.kv_capacity_bytes` 3,472,883,712) claimed. The
priority pass at `MemoryPlan.cpp:223-262` then hands the experts what is left, which is nothing above
their 2 GiB minimum: an explicit `--expert-memory` sets `plan.expertBytes` to the store's charged
bytes (line 247) and only `auto` extends it (line 255), and the extension here computed to zero at
every cap tried.

## Runtime growth is refused for a reason that is not the Metal cap

After the 65k row: `governor_charged_bytes` 9,124,578,204, `headroom_bytes` 2,514,795,620 under an
11,639,373,824 limit, and `growth_allowed` False with 10,703 denied reservations. The device has
2.5 GiB of room under the cap that it will not spend, because `host_headroom_bytes` is 0 (2,403,975,168
spare against a 2,147,483,648 macOS reserve) and `memory_pressure` sits at `warning` with 1.28 GiB of
swap in use. On a 16 GB Mac the room under the Metal cap and the room the operating system has are
different budgets, and the smaller one wins.

## The 16 GiB quota is a real improvement

- Startup restored the persistent cache: `took back 83 restore points over 5314 KV blocks (7076 MiB);
  left 0 copies behind`. The 8 GiB quota could not hold that.
- Cache directory grew to 11.57 GiB during the four rows, 43% past the old quota, with 80.97 GiB free
  on the volume.
- The 65,451-token cold prompt ran 436.4 s / 150.0 tok/s against the 445.7 s / 146.7 tok/s the evening
  run measured at the 8 GiB quota, a 2% difference inside the run-to-run spread. Its KV never spilled: `kv_demotions` +0 and
  `disk_used_bytes` unchanged, because 65,451 tokens is 867 MB against a 2,993 MiB resident allowance.
  The 28,589-token cold row is the one that touched disk, 13 demotions and 0.48 GiB written.
- The repeated 28,589-token prompt still costs 1,178 ms, and this time the source changed:
  `cache.hits` +1, `kv_hit_tokens` +28,576, `kv_disk_hit_tokens` +0, `disk_read_bytes` +0, no KV
  demotion on the repeat. With 262,137 tokens of resident KV allowance the prefix stayed in the
  in-RAM page cache, where V1's same row had to restore 893 blocks and 442.5 MB from disk. The disk
  tier is the fallback, not the fast path, and the larger quota is what keeps prefixes from being
  evicted into it.

## Where this leaves the tuning plan

The `--expert-memory` lever is closed on this machine at 131,072 context: 2 GiB, 4 GiB, explicit or
auto, all produce the same 512-slot, 1,992 MiB, 2% store, and the store cannot grow at runtime
either. Two levers remain, and they attack different numbers:

1. **Lower the served context** (`SPLASH_FLASH_NEXT_MAX_CONTEXT=32761`, `--expert-memory auto`).
   The resident KV allowance is the one reservation this profile controls, and every GiB of it is
   worth about 263 expert slots. Prediction: 32,761 context frees roughly 1.3-1.7 GiB of KV floors,
   which the auto pass can give the experts. Accept only if `cap_bytes > floor_bytes`, `regrows > 0`,
   `hit_rate > 0.01`, and decode clears 13 tok/s; otherwise the profile keeps 131,072 context and
   accepts 11.5-12 tok/s decode.
2. **Stream fewer bytes per token.** At 452-546 MB per emitted token and IQ3_XXS experts, decode is
   the drive, not the GPU. A smaller expert quantization is the only change that raises decode
   without asking a 16 GB machine for memory it does not have.
