# Option 21 (Flash-Next Q2_0 + BF16 DFlash2): the 2,048-token chunk is the fast one, and the launcher now uses it

`qwen38-option21-q2-0-bootstrap-20261110.md` concluded that option 21 cannot warm up a
2,048-token prefill chunk and set its default to 10G with 1,024-token chunks. That
conclusion came from one cold boot and the engine's fixed 5 s Metal event window, not from
measurement. Measured on this M5 (16 GiB, 131072 context, INT8 KV, BF16 state, one active
request), the 2,048-token chunk is the faster profile by a wide margin, so option 21 now
runs the same pair option 20 uses: **10.8G Metal cap with 2,048-token prefill chunks**.

## Why the timeout is marginal rather than fatal

Prefill runs as one command whose dispatches are split by host steps. Metal fails a command
buffer whose event wait is still unmet 5 s after its queue reached it
(`kIOGPUCommandBufferCallbackErrorTimeout`), and the queue reaches a step as the command is
submitted, so the GPU work between two consecutive host steps must end within 5 s
(`docs/internals.md`, `runtime/metal/MetalBackend.hpp:230`).

A 2,048-token chunk at the throughputs below is 4.6-5.0 s of GPU work per chunk: right on
that window. The boot that failed (`...-20261110-141211.log`) reported step 156 of 239 at
5.157 s - the expert store was at its floor and read experts from SSD. The boot that now
runs with the same settings reaches Ready in 16 s with no timeout line, because the store
holds its chunks:

```text
[21:45:47] Launcher: ... prefill_chunk=2048 cache_disk=16G cache_mode=persistent
[21:45:54] Routed experts stream from their files: 2104 slots for 24576 experts (8%) in
           2773 MiB, a store of 3224 MiB in 2 chunks ...
[21:46:02] Expert store gave back a chunk of 421 MiB while memory is short, in 32.9 ms:
           279 experts moved below it and 320 evicted; 1 of 2 chunks hold 1784 slots.
[21:46:03] Ready - ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-GGUF:Q2_0 - context 128K
```

So the chunk size is worth taking, and the launch needs a way back down when a host cannot
warm it up. `startllamacpp.sh` retries a `GPU Timeout` bootstrap failure once with 10G and
1,024-token chunks, logs what it did, and never silently downgrades for any other error.

## Prompt processing: 1,024 vs 2,048 tokens per chunk

Cold prefill, `dev/benchmarks/option20_serving_matrix.py --group prefill`, thermal fair.
1,024 was the previous option-21 default (10G cap); 2,048 is the new one (10.8G cap).

| Prompt tokens | 1024 chunk: tok/s (TTFT s) | 2048 chunk: tok/s (TTFT s) | Change |
|---:|---:|---:|---:|
| 140 | 46.9 (2.99) | 48.4 (2.90) | +3% |
| 524 | 147.3 (3.56) | 123.1 (4.26) | -16% |
| 1,036 | 204.3 (5.07) | 225.4 (4.60) | +10% |
| 2,060 | 248.1 (8.31) | 339.0 (6.08) | +37% |
| 4,108 | 272.2 (15.09) | 395.4 (10.39) | +45% |
| 8,204 | 282.3 (29.06) | 411.8 (19.92) | +46% |

A second 2,048 run a few hours earlier measured 443.7 tok/s at 8,204 and 441.4 at 4,108,
so the gain at long prompts is 40-57% with about 8% run-to-run spread. 512-token prompts are
the one case where the bigger chunk loses: the chunk is not full, so the group's fixed row
stride pays for rows it does not use.

1,536-token chunks, tried as a middle ground, are worse than both at every size above 1K
(320.3 tok/s at 8,204, 331.0 at 4,108, 260.9 at 2,060): half the chunk's benefit with none
of the group's amortization. 2,048 is also the engine's ceiling -
`RuntimeGeometry::from` accepts only multiples of 128 in `[128, 2048]`.

## Decode and long conversations

| | 1024 chunk | 2048 chunk |
|---|---:|---:|
| Coding probes, decode mean | 17.68 tok/s | 17.14 tok/s |
| Coding draft acceptance | 252/263 (95.8%) | 257/265 (97.0%) |
| Ladder turn-1 TTFT | 7.515 s | 6.335 s |
| Ladder turn-8 TTFT | 9.697 s | 7.048 s |
| Ladder turn-8 prefill | 190.7 tok/s | 262.3 tok/s |
| Ladder draft acceptance | 85.9% | 87.8% |

Decode is unchanged: the chunk only shapes prefill. The turn ladder re-sends the whole
conversation, and turn-8 (14,009 prompt tokens, 87% cached) reaches first token 27% sooner.
The coding probes show 3 whole-page KV restores and 96 disk KV read-back tokens, so the KV
spill path is exercised, not avoided; the ladder shows none.

## What changed

`startllamacpp.sh` (byte-identical to `~/startllamacpp.sh`):

- `splash_flash_next_q2_profile()` no longer downgrades the pair; option 21 inherits the
  16 GiB host preset that option 20 already uses.
- The prefill-chunk raise now needs the whole stock profile, including the streamed stores:
  with `SPLASH_FLASH_NEXT_EXPERT_MEMORY` or `SPLASH_FLASH_NEXT_PLE_MEMORY` raised by hand the
  chunk stays 1,024, because a 4G expert store on a 10G cap with 2,048-token chunks plans
  10,940 MiB of floors against a 10,240 MiB budget and the engine refuses to start.
- The launch loop retries a `runtime bootstrap failed ... GPU Timeout` attempt once with
  10G / 1,024 for options 20 and 21, then exits as before if that attempt fails too.
- The menu and the launch banner state the pair and the fallback:

```text
Option 21 profile: 10.8G Metal cap with 2048-token prefill chunks, the pair option 20 uses
on a 16 GiB Mac; it measured 443.7 tok/s cold prefill at 8,204 prompt tokens against 282.3
with 1,024-token chunks. If the warmup trips the engine's 5 s Metal event window, the
launcher retries with 10G and 1,024-token chunks.
```

## Tests

`dev/benchmarks/test_bonsai_launcher.py`, 51 tests, pass against both copies of the launcher:

- `test_option21_shares_the_raised_pair_option_20_uses` - options 20 and 21 both get
  10.8G / 2,048 on a 16 GiB host; the banner and `--list` say so.
- `test_option21_falls_back_to_the_stock_chunk_after_a_warmup_timeout` - a mock server that
  prints the `GPU Timeout` bootstrap failure is retried once at 10G / 1,024 with the draft
  still attached, and the retry is logged.
- `test_option21_explicit_cap_outside_the_stock_set_keeps_the_chunk` - a 12G cap alone does
  not buy the bigger chunk.
- `test_option21_streamed_override_note_names_the_pair_it_holds` - with a raised store the
  cap and chunk are held, and the note says how to get the preset back.
