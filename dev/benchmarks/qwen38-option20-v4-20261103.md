# Option 20 V4: two active request lanes at 131,072 context on 16 GB

Measured 2026-11-04 on the MacBook Air (M5, 10 cores, 16 GB unified memory), engine build
`restart0` of the 2026-11-04 launch, model `ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-GGUF:IQ3_XXS`
with the DFlash2 draft, served on port 1235 as `qwen3.8-flash-next-iq3-xxs-splash`.

```sh
SPLASH_FLASH_NEXT_MAX_MEMORY=11G SPLASH_FLASH_NEXT_MAX_ACTIVE_REQUESTS=2 \
SPLASH_FLASH_NEXT_SECOND_LANE_BELOW_GATE=1 bash /Users/mymac/startllamacpp.sh --direct 20
```

The launcher accepted the second request under the new opt-in flag and said so in the run log:
`Native inference concurrency: 2 (FIFO queue across clients; no worker tool-call budget)`, next to
`server_context=131072 cache_disk=16G cache_mode=persistent`. Context stayed at the profile's
131,072 and `--expert-memory` stayed `auto`.

Rows come from `build/validation/option20-v4-20261103/run_v4.py` against the live server: cold rows
with their own `cache_salt`, the repeat row holding that salt fixed, 10 s cooldowns, bounded
count-to-30 and ORCHID probes, a three-request `lane-probe`, and a `parent-child` probe that starts a
28,589-token parent, drops a 20-token child one second behind it, and samples `/status` every half
second. Condensed row data: `dev/benchmarks/qwen38-option20-v4-20261103.json`.

No row is `clean`. This session's own turns run on the same engine, and its requests are 90-97k
tokens with 1,024-token outputs, which is exactly what the contamination rule calls foreign. The
speed rows below are therefore compared against V3 with a margin, while the lane verdict rests on
the counters, which contamination cannot fake.

## Speed is where V3 left it

| Row | V3 (11G cap, 4G floor, 16G disk, 1 lane) | V4 (11G cap, auto, 16G disk, 2 lanes) |
|---|---|---|
| decode-512 TTFT | 5,448 ms | 5,578 ms |
| decode-512 decode | 11.69 tok/s | 10.38 tok/s |
| 28,589 tok cold TTFT | 189,767 ms | 198,426 ms |
| 28,589 tok cold prefill | 150.7 tok/s | 144.1 tok/s |
| 28,589 tok repeat TTFT | 1,178 ms | 1,177 ms |
| tokens per draft cycle | 7.39-7.53 | 7.39-7.53 |

The slow-looking single-request rows are the contaminated ones: the 28,589-token parent of the
`parent-child` probe, which had no foreign request inside its own window on the server's account,
prefilled at 161.0 tok/s and decoded at 11.8 tok/s (`Done · input 28,589 · prefill 28,589/177.56s ·
PP 161.0 tok/s · decode 113/9.59s · TPS 11.8 tok/s`). That is V3's number, so a second lane changed
nothing about the speed of the request that was actually running.

The prefix cache again did its job. The repeat row started in 1,177 ms and prefilled 13 tokens; at
startup the persistent cache `took back 167 restore points over 15911 KV blocks (16358 MiB)` under
its 16 GiB quota. This session's own turns show the same effect continuously: `input 96,155 ·
cached 95,904 · TTFT 5.3s`, `input 97,654 · cached 96,704 · TTFT 8.9s`, each prefilling only 250-950
rows instead of 90,000.

## Two lanes admitted, one lane executed

The `parent-child` probe is the row that decides this.

| Measurement | Value |
|---|---|
| samples with two requests active | 327 of 371 |
| `admission.waiting_concurrency` | 0 in every sample |
| max requests decoding at once | 1 |
| max requests prefilling at once | 1 |
| `scheduler.decode_batches_by_width` | b1 3,237, b2 0, b3 0, b4 0 |
| child wall time | 188.5 s |
| child time spent queued | 186.5 s |
| three small requests at once (lane-probe) | wall 6.637 s, summed 6.613 s, overlap 0.996 |

The child was admitted: it became the second entry of `active_requests` one second after the parent
started, the frontend queue stayed at zero, and `waiting_concurrency` never moved, so the concurrency
limit was not what held it. It then sat in `WaitingResources` for the parent's entire 189 s and
"started", in the server's own log, at 00:51:15, the same second the parent finished. Its 20-token
prompt cost 1.5 s of work once it was allowed to run.

The reason is the governor, not the launcher:

```
limit_bytes 11,639,373,824  charged 9,279,505,308  headroom 2,359,868,516
host_spare_bytes 1,826,029,568  host_reserve_bytes 2,147,483,648  host_headroom_bytes 0
growth_allowed false  denied_reservations 2,052 -> 4,608
```

There is 2.36 GiB of room under the Metal cap, and the engine will not use any of it for a second
request, because the operating system has 1.83 GiB spare and the governor keeps 2.15 GiB for macOS.
The run log repeats the consequence every few seconds while a second request is waiting:
`Memory: growth paused; waiting=1; suspended=0; held=1`. `Engine::resourceWaitSnapshot` counts that
as `waiting_memory` rather than `waiting_concurrency`, which is exactly what the samples show.

So the earlier reading of the situation was wrong in a useful way. The KV pool really is charged once
for 262,144 tokens, two requests at 131,072, and lane state really is reserved for all four batch
positions. Those reservations are not what a second lane needs. What it needs is a growth
reservation at request time, and on this Mac at an 11 GiB cap there is no growth allowed at all.

## What this means for the gate

`SPLASH_FLASH_NEXT_SECOND_LANE_BELOW_GATE=1` did what it was built to do: it let the configuration be
tested instead of assumed, and the measurement answered it. Two lanes on 16 GB are not a memory
capacity problem at 131,072 context; they are a headroom problem created by the cap. At an 11 GiB cap
the machine ends a quiet moment with 1.83 GiB spare against a 2.15 GiB reserve, swap at 2.10 of
3.07 GiB, `memory_pressure` at `warning`, and 4,608 refused reservations. Every second lane is held
behind that refusal.

The next test is therefore a smaller cap, not a smaller context: `SPLASH_FLASH_NEXT_MAX_MEMORY=10G`
with the same 131,072 context and the same two lanes. V1 measured 2.52 GiB of host spare at that cap,
0.37 GiB above the reserve, which is the first configuration on this Mac where `growth_allowed` can
be true and a held child can actually be admitted. The acceptance test is the same one V4 failed:
`decode_batches_by_width` shows b2 above 0 or the sampler shows two requests decoding at once, the
child's queued time drops from 186 s to a few seconds, and neither request loses more than about a
tenth of its throughput.
