## A methodology correction first

`cache_salt` is part of the engine's cache key (`docs/api.md`: a `cache_salt` no
other request uses reads no cached KV). The 2026-11-02 "repeat" rows used fresh
salts, so they were cold by construction. The earlier note that prefix reuse
failed on a repeated smoke prompt is withdrawn: it was the salt, not the cache.
These runs hold the salt fixed when reuse is the thing being measured, and change
it when a cold row is wanted.

## Repeat rows: this is where the quota pays

V1b ran one 28,589-token prompt with a fixed salt, then a different
28,589-token prompt that pushed the first prompt's KV onto the disk tier, then the
first prompt again.

| Row | TTFT | prefill tokens | cached tokens | KV served from | restores | disk read |
|---|---|---|---|---|---|---|
| x-cold | 191,996 ms | 28,589 | 0 | nothing, full prefill | 0 | 0 |
| x-hit-while-resident | 1,202 ms | 13 | 28,576 | RAM | 0 | 0 |
| y-cold-evicts-x | 184,694 ms | 28,589 | 0 | nothing, full prefill | 0 | 0 |
| x-hit-from-disk | 1,204 ms | 13 | 28,576 | disk tier | 893 | 442.5 MB |

A repeated 28.6k prompt costs 1.2 seconds instead of 185-192 seconds, whether its
KV is still resident or has to be read back from the cache: **about 160x on the
time to first token**. Only 13 tokens have to be prefilled; the 893 restored KV
blocks (442.5 MB) arrive inside that 1.2 seconds. Across the run the engine
demoted 107 KV block groups and restored 7,219 of them (3.32 GB read), and the
cache directory grew to 4.44 GB of its 8 GiB quota, leaving 80 GiB free on disk.

That is the number that matters for agent workloads, where the system prompt,
tool schemas and repeated file context are the same prefix thousands of times. It
is far larger than the 5-8% prefill gain the tuning plan estimated for this
change.

## Memory effect, and why the expert store did not grow

| Counter | start of V1 | end of V1b |
|---|---|---|
| governor charged | 9,450,161,052 | 8,581,940,124 |
| governor headroom under the 10 GiB cap | 1,287,257,188 | 2,155,478,116 |
| host spare | 1,766,506,496 | 2,522,759,168 |
| host headroom over the 2 GiB macOS reserve | 0 | 375,275,520 |
| memory pressure | warning | warning |
| expert store cap / floor | 2,089,468,688 / 2,089,468,688 | 2,089,468,688 / 2,089,468,688 |
| expert slots / resident | 512 of 24,576 / 28 | 512 of 24,576 / 34 |
| expert `hit_rate` | 0.00 | 0.00 |

Spilling KV to the disk tier freed about 0.9-1.0 GiB of Metal memory and lifted
host spare from 1.77 GiB to 2.5-2.9 GiB, above the 2.15 GiB the governor reserves
for macOS. Host headroom went from zero to about 0.37 GiB, so the governor's host
gate is no longer what blocks growth.

The store still did not grow. Under `--expert-memory auto` the plan sized the
store at its floor and `shrinks 0` with `regrows 0`, so runtime headroom is not
spent on experts. Raising the store is a launch-time decision, which is what V2
tests.
